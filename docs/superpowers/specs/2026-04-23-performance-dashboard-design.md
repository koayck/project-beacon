# Performance Dashboard — Design Spec

**Date:** 2026-04-23
**Status:** Approved; pending implementation plan
**Owner:** dejie

## Summary

Add a dedicated `/dashboard` route to the Project Beacon frontend that surfaces historical mission telemetry: 6 overview cards, a recent-runs table, and (v2) a live "current mission" strip. Each user command becomes a row in a new `mission_runs` Supabase table, written by the backend at end of stream. The on-scene mission timer is refactored from session-wide to per-command.

## Goals

- Give pitch/demo audiences a dedicated performance screen beyond the live 3D scene
- Establish per-command as the unit of "mission" for metrics (TTFT, duration, rescue time are per-command concepts)
- Provide a persistent historical view so the dashboard is populated the moment it loads

## Non-Goals

- Real-time dashboard updates during a live run (deferred to v2)
- Per-run drill-down pages with full event timelines (expandable rows are enough for v1)
- Cross-session aggregations or organization-level rollups
- Changing the `mission_logs` table or existing logging behavior

## Architecture & Data Flow

```
User types command in CommandPanel
  │
  ▼
Frontend starts per-command timer (scene.tsx)
  │
  ▼
FastAPI streams agent events (SSE)
  │  ├─ Captures started_at, ttft_ms from LiteLLM events
  │  ├─ Counts tool calls, scan detections, supply deliveries in a MissionRunAccumulator
  │  └─ On stream end → writes one mission_runs row to Supabase
  │
  ▼
Frontend stops timer on stream end

─────────────────────────────────────────────

Dashboard page mounts (/dashboard)
  │
  ▼
GET /dashboard → { overview, runs, currentMission? }
  │   ├─ overview: SQL aggregates (6 cards)
  │   ├─ runs: last 50 rows from mission_runs
  │   └─ currentMission: v2 (always null in v1)
  │
  ▼
Renders OverviewCards + RunsTable
```

### Key decisions

- **Backend owns metric collection.** One `MissionRunAccumulator` per command-stream captures everything and writes once at stream end. No frontend races, no UI-state coupling.
- **Single `GET /dashboard` endpoint.** One fetch, one loader state, cheap SQL aggregates alongside the row list.
- **Historical-first.** Dashboard refreshes on navigation (user-triggered). Live push is a v2 stretch goal.
- **Fresh table.** `mission_runs` is new; the existing `mission_logs` is left untouched and keeps working as-is.

## Data Model

### New table: `mission_runs`

```sql
CREATE TABLE IF NOT EXISTS mission_runs (
    id                   BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    simulation_id        TEXT,
    asset_id             TEXT NOT NULL,
    prompt               TEXT NOT NULL,
    status               TEXT NOT NULL,
    started_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    ended_at             TIMESTAMPTZ,
    duration_ms          INTEGER,
    ttft_ms              INTEGER,
    tool_call_count      INTEGER NOT NULL DEFAULT 0,
    survivors_detected   INTEGER NOT NULL DEFAULT 0,
    survivors_rescued    INTEGER NOT NULL DEFAULT 0,
    result_summary       TEXT,
    error_message        TEXT,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX IF NOT EXISTS idx_mission_runs_created_at ON mission_runs (created_at DESC);
CREATE INDEX IF NOT EXISTS idx_mission_runs_simulation ON mission_runs (simulation_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_mission_runs_status     ON mission_runs (status);
```

### Field sources

| Field | Source | Notes |
|---|---|---|
| `simulation_id` | request body | Groups runs by simulation session |
| `asset_id` | request body | `"FLEET"`, `"auto"`, or `"BEACON-XX"` |
| `prompt` | request body | Full natural-language command |
| `status` | end-of-stream | `"success"`, `"failed"`, or `"aborted"` |
| `started_at` / `ended_at` / `duration_ms` | accumulator | `duration_ms` computed in Python on write (no generated column) |
| `ttft_ms` | LiteLLM timing | Already captured in `send_command_stream`'s `first_token_time` |
| `tool_call_count` | accumulator | Increments on each MCP tool invocation observed in the event stream |
| `survivors_detected` | scan events | Count of unique `(x, y, z)` keys from scan_reports / tool_result survivor payloads |
| `survivors_rescued` | supply dispatch events | Count of unique delivered survivor keys |
| `result_summary` | final agent text, truncated to 500 chars | For table preview |
| `error_message` | exception handler | Populated only on `status='failed'` |

### Migration

File: `supabase/migrations/20260424000000_create_table_mission_runs.sql` containing the `CREATE TABLE` and indexes above. Applied via Supabase MCP `apply_migration` so the live DB matches.

### What we leave alone

- `mission_logs` — continues to be written alongside `mission_runs`; untouched schema
- `simulation`, `assets`, `licenses` — no changes
- ADK framework tables (`sessions`, `events`, `app_states`, `user_states`, `adk_internal_metadata`) — owned by Google ADK, not ours

### New repository (`backend/db/repository.py`)

```python
class _MissionRunRepository:
    async def create(self, run: MissionRun) -> int: ...       # INSERT RETURNING id

mission_run_repo = _MissionRunRepository()
```

Overview SQL (one round-trip):

```sql
SELECT
  COUNT(*)                                                        AS total_missions,
  AVG(ttft_ms) FILTER (WHERE ttft_ms IS NOT NULL)                 AS avg_ttft_ms,
  AVG(duration_ms) FILTER (WHERE duration_ms IS NOT NULL)         AS avg_duration_ms,
  SUM(survivors_rescued)                                          AS total_survivors_rescued,
  SUM(survivors_detected)                                         AS total_survivors_detected,
  CASE WHEN SUM(survivors_detected) > 0
       THEN 100.0 * SUM(survivors_rescued) / SUM(survivors_detected)
       ELSE 0 END                                                 AS rescue_success_rate,
  AVG(EXTRACT(EPOCH FROM (ended_at - started_at)))
      FILTER (WHERE status='success' AND survivors_rescued > 0)   AS avg_rescue_time_s
FROM mission_runs;
```

**Note on "avg rescue time":** The card labeled "Avg Rescue Time" displays `avg_rescue_time_s` — average end-to-end duration for successful runs that actually delivered to at least one survivor. Per-survivor detection-to-delivery latency would require per-event timestamps we don't currently persist; this aggregate is a defensible proxy for the pitch and can be refined in v2.

### New accumulator (`backend/services/mission_runs.py`)

```python
class MissionRunAccumulator:
    """Collects per-command metrics across a streaming request."""
    def __init__(self, asset_id: str, prompt: str, simulation_id: str | None):
        self.asset_id = asset_id
        self.prompt = prompt
        self.simulation_id = simulation_id
        self.started_at = datetime.now(timezone.utc)
        self.tool_call_count = 0
        self._detected_keys: set[tuple[float, float, float]] = set()
        self._rescued_keys: set[tuple[float, float, float]] = set()

    def record_tool_call(self) -> None: ...
    def record_detections(self, survivors: list[dict]) -> None: ...  # dedupe by rounded (x,y,z)
    def record_deliveries(self, dispatches: list[dict]) -> None: ... # dedupe by survivor key
    def build(self, *, status: str, ttft_ms: int | None,
              final_text: str, error: str | None = None) -> MissionRun: ...
```

Dedup key-rounding matches the existing `_extract_survivor_coords` convention (3 decimals).

### Wiring into `send_command_stream` (`backend/app.py`)

Inside `generate()`:

- **Create accumulator** right after `stream_start = time.perf_counter()`
- **Track abort flag** in the outer scope — set to `True` when the `request.is_disconnected()` path breaks out of the loop
- **Update accumulator** at these points in the existing event loop:
  - `part.function_call` branch → `acc.record_tool_call()`
  - `tool_result` branch where `survivors_payload` is non-empty → `acc.record_detections(survivors_payload)`
  - `tool_result` branch where `supply_dispatches` is non-empty → `acc.record_deliveries(supply_dispatches)`
- **Determine status in `finally`**:
  - `failed` if a `kind == "error"` was observed
  - `aborted` if the abort flag is set
  - `success` otherwise
- **Write row** via `await mission_run_repo.create(acc.build(status=..., ttft_ms=ttft_ms, final_text=final_text, error=...))`
- The existing `mission_log_repo.create(...)` call stays (cheap insurance, already working)

The non-streaming `/command` endpoint (`backend/app.py:892`) gets the same accumulator treatment for parity — accumulator created at top, updated in the inline event loop, written before returning.

### New endpoint

```python
@app.get("/dashboard")
async def get_dashboard() -> dict:
    overview = await mission_run_repo.overview()
    runs = await mission_run_repo.list_recent(limit=50)
    return {
        "overview": overview,
        "runs": [r.model_dump() for r in runs],
        "currentMission": None,  # v2: populate from in-memory registry if a run is in-flight
    }
```

### What we don't change

- MCP tools, agents, gRPC layer, telemetry — untouched
- `mission_logs` table and its writes — untouched

## Frontend Changes

### New route — `frontend/src/app/dashboard/page.tsx`

Client component (fetches at mount, has interactivity). Renders header with a back link, conditionally renders `CurrentMissionStrip`, then `OverviewCards`, then `RunsTable`. Loading and error states are plain text.

### New components (`frontend/src/components/dashboard/`)

- **`OverviewCards.tsx`** — 6-card responsive grid matching the `MetricsPanel` visual language (dark bg, teal/cyan accents, monospace, tabular-nums). Cards:
  1. Total Missions Run
  2. Avg TTFT (`avg_ttft_ms` / 1000, display as seconds)
  3. Avg Rescue Time (`avg_rescue_time_s`, display as mm:ss)
  4. Rescue Success Rate (`rescue_success_rate`, %)
  5. Total Survivors Rescued
  6. Avg Mission Duration (`avg_duration_ms`, mm:ss)
- **`RunsTable.tsx`** — sortable table. Columns: `#`, `Prompt` (truncated), `Asset`, `Status` (color-coded chip), `TTFT`, `Duration`, `Detected`, `Rescued`, `When` (relative time). Row click expands to show full prompt + `result_summary` + `error_message`.
- **`CurrentMissionStrip.tsx`** — thin horizontal bar at top. Shows in-flight command prompt, live elapsed, pulsing indicator. Hidden when `currentMission` is null. Always null in v1 — strip is plumbed in advance so v2 doesn't need frontend changes.

### New API helper (`frontend/src/lib/api.ts`)

Add `DashboardRun`, `DashboardOverview`, `DashboardPayload` types and a `fetchDashboard(): Promise<DashboardPayload>` function that GETs `/dashboard` from the backend base URL.

### Scene changes — mission timer refactor (`frontend/src/components/scene.tsx`)

1. **Timer resets per command** (line 924): change `setMissionStartTs(prev => prev ?? Date.now())` → `setMissionStartTs(Date.now())`.
2. **Timer stops when stream ends** — introduce a `missionEndTs` state. Set it in the `done`/`error`/finally branches of the SSE handler. Reset to `null` when a new command dispatches.

### MetricsPanel updates (`frontend/src/components/panels/MetricsPanel.tsx`)

- Accept new prop `missionEndTs: number | null`
- Live elapsed uses `(missionEndTs ?? Date.now()) - missionStartTs` when both are set
- Header label: stays `MISSION TIME` while live; switches to `LAST MISSION` with a muted color once `missionEndTs` is set

### TopStatusBar (`frontend/src/components/panels/TopStatusBar.tsx`)

Add a small link/button in the top-right that navigates to `/dashboard`. Label: `PERFORMANCE →` or similar.

### What we don't change

- WebSocket bridge, 3D scene, fog of war, activity panel, command panel, all other scene props

## Error Handling & Edge Cases

| Scenario | Behavior |
|---|---|
| Supabase write fails at end of stream | Log error, don't fail the stream. User already got the response. |
| User disconnects mid-stream | Status `aborted`; partial metrics (duration, partial detections/rescues) persisted. |
| Agent raises exception | Status `failed`; `error_message` populated via `_first_exception_message`. |
| `duration_ms` > INT max | Capped at `2_147_483_647`. Not expected in practice. |
| `/dashboard` with zero runs | `overview` returns zeros/nulls; frontend shows "No missions yet — run a command to populate." |
| Stale `currentMission` (backend crashed) | v1: always null. v2: in-memory registry with startup cleanup pass. |
| Same survivor detected twice in one run | Deduped by rounded `(x, y, z)` key; counts as 1. |
| Same survivor detected AND rescued in one run | Counts as 1 detected + 1 rescued (independent sets). |
| Clock skew (`started_at > ended_at`) | Clamp `duration_ms` to 0 on write. |

## Rollout

Single shippable PR:

1. Apply migration `20260424000000_create_table_mission_runs.sql` via Supabase MCP `apply_migration`
2. Backend: model, repository, accumulator, `/dashboard` endpoint, stream wiring
3. Frontend: new route, components, api helper, timer refactor, TopStatusBar link
4. Run 5–10 commands locally before the demo so the dashboard has populated history

## Deferred to v2

- **Live `currentMission`** — backend in-memory registry of in-flight runs exposed via `/dashboard`. Frontend stub is already in place. ~40 LOC backend addition.
- **WebSocket push** — broadcast `mission_run_completed` so open dashboard auto-refreshes.
- **Per-mission detail page** (`/dashboard/runs/[id]`) — full result text, event timeline. Expandable row is enough for v1.
- **Per-survivor rescue latency** — persist per-event timestamps and compute true detection→delivery time. Current aggregate (`avg_rescue_time_s`) is a proxy.
